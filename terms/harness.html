Harness

韁繩

模型只負責產生文字，其餘全部是外面那一層在做。

定義

Harness 是包在模型外面的那一整層程式。

模型自己只做一件事：讀進一段文字，吐出一段文字。它不會查資料庫、不記得上一輪發生什麼、也不知道任務到底完成了沒有。這些全部是 harness 在做：

組上下文
這一輪要餵進去的東西：任務、前幾輪結果、可用的工具清單
接住輸出
看模型吐出來的文字裡有沒有<a href="tool-use.html" class="term-link" data-term="tool-use">工具呼叫</a>的格式
實際執行
真的去查、去寫、去送出
回填結果
把執行結果變成下一輪的輸入
判斷收工
還沒完成就再跑一輪，跑太多輪就停下來

英文 harness 原意是套在馬身上的整套挽具——韁繩只是其中一條。分工也剛好一樣：馬提供力量，挽具決定這股力量接到哪台車、往哪個方向。

所以「harness engineering」講的是把工夫從調模型，移到調外面這一層。

為何會出現

以前模型是主要變因，換一個更強的模型，什麼都會變好。現在前段班的模型能力已經接近，同一個模型包在不同的 harness 裡，差距常常比換模型還大。

差在哪？工具描述寫得含糊，它就挑錯工具；上下文塞滿雜訊，真正重要的那句被埋掉；迴圈沒有停止條件，它就在原地鬼打牆。這幾件事換模型都不會好。

跟護欄很容易搞混，但兩者管的層次不同：

管什麼
Harness 它怎麼運作——看得到什麼、做得到什麼、能試幾次
護欄 它不准做什麼——工具清單、權限範圍、出向管控

護欄是裝在 harness 上的。沒有 harness，就沒有地方裝護欄。代理治理再往上一層，是把這些機制加上紀錄一起管的制度。

金融背景怎麼理解

兩個能力差不多的理專，一個手上有整合好的客戶系統、有現成的商品比較表、有覆核流程接著；另一個每件事都要自己翻。半年後產出差一大截——差的不是人。

這件事在導入時最常被跳過。開會問的第一句常常是「我們要用哪一家的模型」，但實際決定成敗的是下面這幾題：

實際上會問的問題 其實在問 harness 的哪一塊
它查得到哪些資料？ 工具怎麼定義、開了什麼權限
它記不記得上一步做了什麼？ 上下文怎麼組進去的
它會不會一直重複做同一件事？ 迴圈的停止條件
出錯之後查不查得到？ 每一輪的紀錄留在哪
換更強的模型，補不了 harness 的洞

如果它現在會挑錯工具、會忘記任務目標、會鬼打牆，那多半不是模型不夠聰明，是外面那層沒寫好。同一組問題換一個模型，通常只會換一種出錯方式。

實務上的意涵：這一層是我們自己的工程資產，不是廠商給的。模型會一直換，但工具怎麼定義、紀錄留成什麼樣子、哪一步要停下來讓人確認，這些留得下來。

提示詞工程 vs Harness Engineering

都是讓 AI 表現更好的手段，差在「調整問法」還是「設計環境」

提示詞工程（Prompt Engineering）
是什麼
透過精心設計輸入文字（提示詞），引導 AI 給出更好的輸出；包含角色設定、few-shot 範例、思考鏈（CoT）等技巧
優勢
門檻低、不需改動系統架構、任何人都能嘗試；迭代快速
劣勢
效果受限於模型本身能力；單次對話有效，跨任務的可靠性難以保證；Agent 多步驟執行時容易出錯
適合
單次問答優化、快速原型驗證、非工程師改善 AI 輸出品質
Harness Engineering（線束工程）
是什麼
設計 AI Agent 執行環境的工程實踐：規定 Agent 能用哪些工具、能存取哪些資料、輸出如何被驗證、以及何時應該停下來。核心公式：Agent = 模型 + Harness
優勢
讓 Agent 可預測、可稽核、可靠；透過環境約束降低 AI 出錯與越權風險；適合正式上線的生產環境
劣勢
需要工程師設計與維護；前期建置成本高；需要對業務流程有深度理解才能設計好邊界
適合
需要長期穩定運行的 AI Agent 自動化系統；高合規要求的金融、法務場景
核心差異

提示詞工程是「改善和 AI 說話的方式」，解決的是單次輸出品質；Harness Engineering 是「設計 AI 能做什麼、不能做什麼的環境」，解決的是 Agent 長期可靠性。兩者不互斥：好的 Harness 裡通常也有精心設計的提示詞，但光靠好提示詞無法讓 Agent 安全地自主運作。

金融業應用情境

提示詞工程：讓 AI 用更精準的語氣生成法規摘要、調整輸出格式符合內部報告規範。Harness Engineering：設計 AI 法規審查 Agent 的工具存取範圍（只能讀，不能改）、輸出必須經人工確認後才能送出、超過信心門檻才自動執行
